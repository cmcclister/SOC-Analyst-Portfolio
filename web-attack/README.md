# Investigation #3 — "Web Attack Investigation"

> **Environment:** TryHackMe lab — *Detecting Web Attacks*, Task 4: “Log-Based Detection”  
> **Evidence reviewed:** `access.log` excerpt supplied with the lab  
> **Scope:** Directory discovery, suspected login brute force, and a suspected SQL injection attempt  
> **Source:** [TryHackMe — Detecting Web Attacks](https://tryhackme.com/room/detectingwebattacks)

## Executive summary

The access log shows a source IP—redacted in the supplied evidence—making rapid requests to a web application. The activity begins with directory discovery using the `FFUF v2.1.0` user agent. It is followed by repeated requests to `/login.php`, including a `POST` request that receives a `302` response, and then requests to `/account` and `/account/changeusername.php`.

The final request contains a URL-encoded SQL-like expression: `%' OR '1'='1`. This is consistent with a SQL injection attempt. Taken together, the sequence is suspicious and merits investigation. However, the access log alone does **not** prove that authentication succeeded or that SQL injection worked: the meaning of the `302` depends on the application’s behavior, and the final `200` response only shows that the server returned a response.

## Investigation narrative

### 1. HTTP requests: discovery and probing

The first requests use `FFUF v2.1.0` as the user agent and probe multiple paths, including `/login.php`, `/social`, `/images`, `/manage`, `/corporate`, `/company`, `/files`, `/home`, `/catalog`, and `/products`. Some requests receive `200` responses, while others receive `404` responses.

This pattern is consistent with automated directory or content discovery: a client tries candidate paths and compares responses to identify potentially interesting routes. A `200` response means the server returned a successful HTTP response, but it does not by itself prove that the path is a valid or useful application feature. The response body, application behavior, and any soft-404 behavior should also be checked.

### 2. Application behavior: login attempts and account access

The log then shows repeated requests to `/login.php`, followed by a cluster of `POST` requests to the same endpoint. Most of the displayed POST requests return `200`; one returns `302`. The source subsequently requests `/account`, which returns `301`, and `/account/`, which returns `200`.

This sequence is consistent with repeated login attempts followed by a redirect and access to account-related routes. A `302` indicates a redirect, not proof of successful authentication. To determine whether login succeeded, correlate the request with the `Location` response header, session or authentication logs, and the application’s expected behavior for failed and successful logins.

### 3. Log evidence: the SQL injection indicator

The last displayed request is:

```http
GET /account/changeusername.php?q=%25%27+OR+%271%27%3D%271 HTTP/1.1
```

URL-decoding the `q` parameter yields:

```text
%' OR '1'='1
```

The expression is a recognizable SQL injection probe intended to alter the logic of a database query. The request’s user agent is `sqlmap/stable`, which is additional context that the request may have been generated by an automated SQL injection testing tool. Neither the payload nor the user agent proves that the application was vulnerable or that the input was executed as SQL.

## Attack chain assessment

| Stage | Observed evidence | Assessment |
|---|---|---|
| Reconnaissance | Rapid path requests using `FFUF v2.1.0`; mixed `200` and `404` responses | Consistent with automated directory discovery |
| Login probing | Repeated `POST /login.php` requests in quick succession | Consistent with password-guessing or brute-force activity; request bodies are not shown |
| Possible authentication transition | A login POST receives `302`; later requests target `/account` | Suspicious sequence, but the redirect alone does not confirm successful authentication |
| SQL injection attempt | Encoded parameter on `/account/changeusername.php` decodes to `%' OR '1'='1`; user agent is `sqlmap/stable` | Strong indicator of an attempted SQL injection; success is not established by this access log |

## Indicators of compromise

- **Source:** `192.168.1.[REDACTED]`  
  The address is anonymized in the evidence and may be a lab-internal address rather than a real-world public indicator.
- **User agent during path discovery:** `FFUF v2.1.0`
- **User agent on the final request:** `sqlmap/stable`
- **Targeted endpoints:** `/login.php`, `/account/`, and `/account/changeusername.php`
- **Observed payload:** `%' OR '1'='1`
- **Behavioral indicators:** Rapid path enumeration and repeated login POST requests

Treat these indicators as investigation leads, not as proof of a successful compromise. User-agent strings can be changed or spoofed, and an IP address should be assessed in its network and lab context.

## Detection opportunities

A useful detection should correlate behavior across the sequence rather than alerting on a single request:

1. **Directory discovery:** Alert on many distinct paths requested by one source in a short window, particularly when responses include a mix of successful and missing paths.
2. **Login guessing:** Alert on repeated `POST` requests to `/login.php` from one source or against one account within a defined interval. Where possible, use application authentication logs to distinguish failed and successful attempts.
3. **Suspicious redirect and account access:** Enrich a login alert when a redirect is followed by access to an authenticated route. Confirm the meaning of the redirect using application-specific behavior.
4. **SQL injection indicators:** Inspect query parameters for suspicious SQL syntax and correlate the request with application, database, and WAF events. Avoid relying on a user-agent match alone.

**Analyst validation:** Review response bodies and headers, authentication outcomes, session creation, application errors, and database-side evidence. Check whether the account details changed and whether any other requests or actions followed.

## Response and remediation

- **Contain and scope:** If investigation confirms malicious activity, block or rate-limit the source as a short-term measure where appropriate. Search for related requests from the same source and for similar activity from other sources. Because the address in this evidence is redacted and appears lab-internal, do not use it as a production block indicator without validating its context.
- **Protect authentication:** Apply rate limits and progressive delays to login attempts; monitor failures by source and account; use MFA where appropriate; and review account activity for unauthorized access.
- **Fix the SQL injection risk:** Use parameterized queries or prepared statements so user input is treated as data, not SQL. Apply server-side input validation as a complementary control; input sanitization alone is not a reliable SQL injection defense.
- **Improve logging and monitoring:** Record authentication outcomes, session creation, relevant response headers, and application/database errors. Ensure sensitive values such as passwords and session tokens are not written to logs.
- **Verify recovery:** If unauthorized access or data changes are confirmed, follow the organization’s incident-response process, including account/session containment, impact assessment, and recovery.

## Conclusion

This investigation demonstrates how HTTP-level observations can be translated into application and security questions: What paths were requested? How did the application respond? Did authentication actually succeed? Was the supplied parameter merely received, or did it affect a database query?

A web development background is useful here because it helps connect routes, methods, parameters, redirects, and application behavior to the evidence in the logs. From a SOC perspective, the key is to turn those observations into a testable hypothesis, correlate them with other telemetry, and avoid treating suggestive evidence as confirmation without validation.
